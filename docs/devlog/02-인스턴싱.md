# [MiniBlender #2] 인스턴싱 — 드로우콜 10,002개를 2개로

[지난 글](01-드로우콜.md)에서 드로우콜이 얼마나 비싼지 쟀다. 큐브 10,000개를 그리면 CPU 3.09 ms, 콜당 0.31 µs. GPU는 놀고 있었다.

이번엔 그걸 줄인다. **인스턴싱**이다.

---

## 문제는 "몇 번 부탁했느냐"

지난 글의 결론을 다시 적으면 이렇다.

> 요즘 GPU에게 삼각형 100만 개는 아무것도 아니다. 문제는 삼각형이 아니라 **몇 번 부탁했느냐**다.

큐브 10,000개짜리 씬에서 CPU가 하는 일은 이거다.

```cpp
for (오브젝트 10,000개)
{
    setMat4("model", ...);      // uniform 업로드
    setVec3("objectColor", ...); // uniform 업로드
    glBindVertexArray(...);      // VAO 바인딩
    glDrawElements(...);         // 드로우콜
}
```

**10,000개가 전부 같은 큐브 메시를 쓴다.** 정점 데이터는 GPU에 하나만 올라가 있고 오브젝트들은 그걸 가리키기만 한다. 그런데도 우리는 만 번을 따로 부탁하고 있다. 다른 건 `model` 행렬과 색뿐인데.

인스턴싱은 이 상황을 정확히 겨냥한다. GPU에게 이렇게 말한다.

> "이 큐브를, 여기 있는 변환 행렬 10,000개 각각에 대해 한 번씩 그려. 한 번에 다."

---

## uniform을 버퍼로 옮긴다

인스턴싱의 전부는 **오브젝트마다 밀어넣던 값을 버퍼에 미리 쌓아두는 것**이다.

지금 `model`은 uniform이다. uniform은 드로우콜과 드로우콜 사이에 바뀌는 값이라, 값이 바뀌려면 드로우콜이 끊겨야 한다. 반대로 정점 attribute(`position`, `normal`)는 **한 드로우콜 안에서** 정점마다 바뀐다.

그래서 `model`을 uniform이 아니라 **attribute로** 만든다. 대신 읽는 속도를 바꾼다.

| | 어디서 읽나 | 언제 다음 칸으로 |
|---|---|---|
| `position`, `normal` | 바인딩 슬롯 0 | **정점**마다 (divisor 0) |
| `model`, `color` | 바인딩 슬롯 1 | **인스턴스**마다 (divisor 1) |

큐브의 정점 24개를 훑는 동안 `model`은 고정이고, 다음 큐브로 넘어갈 때 한 칸 전진한다. 이 "언제 전진하느냐"가 divisor다.

```cpp
//Mesh.cpp — 이 한 줄이 인스턴싱의 스위치다
glVertexArrayBindingDivisor(vao, 1, 1);
```

DSA에서는 divisor를 attribute가 아니라 **바인딩 슬롯**에 건다. 그래서 attribute 5개(mat4 4칸 + 색 1칸)에 한 번만 걸면 된다.

### 함정 1 — mat4는 attribute 한 칸에 안 들어간다

GL의 attribute 한 칸은 `vec4`가 최대다. `mat4`는 그 4배라 **네 칸을 먹는다.**

```cpp
for (unsigned int col = 0; col < 4; ++col)
{
    const unsigned int loc = 2 + col;   // location 2,3,4,5를 model이 다 쓴다
    glEnableVertexArrayAttrib(vao, loc);
    glVertexArrayAttribFormat(vao, loc, 4, GL_FLOAT, GL_FALSE,
        (GLuint)(offsetof(InstanceData, model) + col * sizeof(glm::vec4)));
    glVertexArrayAttribBinding(vao, loc, 1);
}
```

셰이더에서는 그냥 `in mat4`로 받으면 GL이 알아서 다시 합쳐준다. 다만 **다음 attribute는 6번부터** 시작해야 한다. 무심코 3번을 색에 쓰면 행렬 두 번째 열을 색으로 덮어쓰게 되고, 화면에는 큐브가 기괴하게 늘어난 채로 나온다.

```glsl
layout (location = 2) in mat4 aInstanceModel;   // 2,3,4,5를 먹는다
layout (location = 6) in vec3 aInstanceColor;   // 그래서 6부터
```

### 함정 2 — 켜둔 attribute는 버퍼가 없어도 읽으려 든다

처음엔 메시를 만들 때(`Upload`) 인스턴스 attribute를 미리 켜두려 했다. 그런데 이러면 **인스턴싱을 끈 경로에서 문제가 된다.** attribute가 켜져 있으면 GL은 바인딩 슬롯에 버퍼가 없어도 거기서 값을 읽으려 하고, 그건 정의되지 않은 동작이다.

그래서 형식 설정을 늦췄다. 인스턴싱 경로가 **처음 그 메시를 그릴 때** 한 번만 잡고, 이후엔 "어느 버퍼의 어디부터 읽을지"만 바꾼다.

```cpp
void Mesh::BindInstanceBuffer(unsigned int instanceVBO, size_t byteOffset)
{
    if (!instanceAttribsReady) { /* attribute 형식 설정 + divisor */ }
    glVertexArrayVertexBuffer(vao, 1, instanceVBO, (GLintptr)byteOffset, sizeof(InstanceData));
}
```

## 제출하는 쪽은 안 건드렸다

지난 글에 이렇게 써뒀었다.

> `Mesh`는 데이터만 들고 있을 뿐 그리는 법을 모른다. 인스턴싱으로 갈아끼울 때 **제출하는 쪽(`Scene`, `SceneObject`)은 안 건드리고 실행하는 쪽만** 바꾸려는 것이다.

실제로 그렇게 됐다. `Scene`과 `SceneObject`는 **한 줄도 안 고쳤다.** 오브젝트가 처음부터 메시를 포인터로 공유하고 있어서(`SceneObject::mesh`), 같은 메시를 쓰는 오브젝트를 모으는 건 포인터 비교로 끝난다.

```cpp
//같은 메시끼리 모으고 → 한 버퍼에 통째로 올리고 → 메시당 콜 하나
for (const SceneObject& obj : scene.GetObjects())
{
    // obj.mesh 포인터가 같은 것끼리 묶어 InstanceData를 쌓는다
}

glNamedBufferSubData(instanceVBO, 0, bytes, instanceScratch.data());

for (const InstanceGroup& group : instanceGroups)
{
    group.mesh->BindInstanceBuffer(instanceVBO, group.first * sizeof(InstanceData));
    glBindVertexArray(group.mesh->GetVAO());
    glDrawElementsInstanced(GL_TRIANGLES, group.mesh->GetIndexCount(),
                            GL_UNSIGNED_INT, nullptr, (GLsizei)group.count);
}
```

메시 종류가 몇 개든 **드로우콜은 메시 종류 수만큼**이다. 큐브 10,000개면 1개(+그리드 1개).

### 원래 경로를 지우지 않았다

`Renderer::useInstancing`을 두고 껐다 켤 수 있게 했다. 통계 패널의 체크박스이자 측정 모드의 `--no-instancing` 플래그다.

비교 대상을 코드에서 지워버리면 다음에 또 만들어야 한다. 이 프로젝트의 작업 방식이 "같은 씬을 켜고/끄고 재서 비교"인 이상, 기준선은 **실행 가능한 상태로** 남아 있어야 한다.

셰이더도 프래그먼트 쪽은 **같은 파일을 쓴다.** 바뀐 건 정점을 어디에 놓느냐뿐이고 픽셀을 칠하는 비용은 두 경로가 완전히 동일해야, 나온 차이를 인스턴싱 덕이라고 말할 수 있다. 노멀 계산의 `inverse()` 같은 비싼 연산도 한쪽만 빼지 않고 그대로 뒀다.

## 측정

**환경**: RTX 3060 / Release x64 / vsync off / 1280×720
**방법**: 워밍업 120프레임 후 300프레임 평균, 조건당 3회 실행해 최소값

```bash
MiniBlender.exe 10000 Cube 120 300 --no-instancing   # 기준선
MiniBlender.exe 10000 Cube 120 300                   # 인스턴싱
```

큐브 10,000개 기준으로 **드로우콜 10,002 → 2, CPU 3.60 → 1.18 ms (3.0배), 프레임 3.91 → 1.51 ms (2.6배)**.

**삼각형 수는 두 줄이 정확히 같다.** GPU가 처리하는 양은 하나도 안 줄었다. 줄어든 건 "그려라"라고 말한 횟수뿐이다. 이게 인스턴싱이 하는 일의 전부다.

## 예상 못 한 것 — GPU 시간도 같이 떨어졌다

계획은 "CPU만 줄고 GPU는 그대로일 것"이었다. 그리는 양이 같으니까. 그런데 10,000개에서 **GPU가 1.94 → 0.17 ms로 11배** 떨어졌다.

드로우콜은 CPU만 먹는 게 아니었다. GPU 앞단(커맨드 프로세서)도 콜 하나마다 상태를 세팅하고 파이프라인을 준비하는 고정 비용을 낸다. 큐브 하나에 삼각형 12개면 그 준비 비용이 실제 그리는 비용보다 크다. **GPU도 잔심부름에 시간을 쓰고 있었던 것이다.**

지난 글에서 "GPU는 놀고 있다"고 썼는데, 정확히는 **놀면서도 잔업이 있었다**가 맞다.

## 안 통하는 경우도 재봤다

인스턴싱이 만능처럼 보이면 안 되니까 반대 케이스도 쟀다. 고해상도 구(16,128 삼각형) 64개다.

| | 드로우콜 | 삼각형 | CPU | GPU | 프레임 |
|---|---:|---:|---:|---:|---:|
| off | 66 | 1,032,205 | 0.062 ms | 0.196 ms | 0.297 ms |
| **on** | **3** | 1,032,205 | 0.049 ms | 0.199 ms | 0.292 ms |

**아무 차이도 없다.** 드로우콜은 66 → 3으로 줄었는데 프레임은 0.297 → 0.292 ms, 오차 범위다.

당연하다. 이 씬은 콜이 66개뿐이라 애초에 CPU가 병목이 아니었다. GPU가 삼각형 103만 개를 실제로 갈고 있고, 그 양은 인스턴싱으로 안 줄어든다. **CPU 바운드가 아닌 씬에 인스턴싱을 넣으면 아무 일도 일어나지 않는다.**

지난 글의 CPU/GPU 분리 표시가 여기서 값을 한다. 어느 쪽이 병목인지 보고 나서 기법을 골라야 한다.

---

## 남은 CPU 1.18 ms는 뭔가

큐브 10,000개에서 콜은 2개인데 CPU가 아직 1.18 ms다. 콜당 0.36 µs였던 걸 감안하면 콜 2개는 1 µs도 안 된다. 나머지는 어디 갔나.

**행렬을 만드는 데 쓴다.** 매 프레임 오브젝트마다 이걸 돈다.

```cpp
const InstanceData data{ obj.transform.GetMatrix(), obj.color, 0.0f };
```

`Transform::GetMatrix()`는 translate + rotate 3번 + scale = 행렬 곱 5번이다. 그걸 10,000번 하고, 800 KB를 GPU에 올린다. 인스턴스 1개당 0.118 µs — 드로우콜 하나 값(0.36 µs)의 3분의 1이 **행렬 하나 값**인 셈이다.

여기서 알 수 있는 게 하나 더 있다. 지난 글에서 잰 "콜당 0.31 µs"에는 사실 이 행렬 계산이 섞여 있었다. 순수한 드로우콜 비용은 그보다 낮다.

이건 인스턴싱과 별개 문제라 이번엔 안 건드렸다. 다음 후보다.

- **행렬 캐싱** — 안 움직인 오브젝트의 행렬을 다시 계산하지 않는다 (Transform에 더티 플래그)
- **프러스텀 컬링** — 화면 밖 인스턴스는 버퍼에 넣지도 않는다. 지금은 카메라 뒤에 있어도 전부 올린다
- **MultiDrawIndirect** — 서로 다른 메시들까지 한 콜로. 지금은 메시 종류만큼 콜이 늘어난다

## 정리

| | 전 | 후 |
|---|---:|---:|
| 드로우콜 | 10,002 | **2** |
| CPU | 3.60 ms | **1.18 ms** |
| GPU | 1.94 ms | **0.17 ms** |
| FPS | 256 | **660** |

한 줄로 줄이면 이렇다. **같은 메시를 여러 번 그릴 때, 다른 건 행렬뿐이라면 uniform을 버퍼로 옮기고 divisor를 걸어라.**

그리고 이번에도 확인한 건, 넣기 전 숫자가 있어야 넣은 후 숫자가 의미를 갖는다는 것이다. 고해상도 구 케이스처럼 **아무 효과가 없는 경우를 알아채려면** 특히 그렇다.
