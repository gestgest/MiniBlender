# [MiniBlender #1] 드로우콜은 얼마나 비싼가 — 직접 재봤다

미니 블렌더를 만들기로 했다. 목표는 "블렌더 클론"이 아니라, **DCC 툴의 뼈대를 핑계 삼아 그래픽스 최적화 기법을 하나씩 넣어보는 것**이다.

그래서 첫 글부터 기능이 아니라 **드로우콜** 이야기다. 순서를 이렇게 잡은 이유가 있다.

---

## 왜 기능보다 계측이 먼저인가

최적화 프로젝트에서 제일 흔한 실패가 이거다.

> "인스턴싱 넣었더니 빨라진 것 같아요"

**같아요**로 끝나면 아무것도 증명한 게 없다. 넣기 전 숫자가 없으니까. 그래서 오브젝트를 그리는 코드보다 **재는 코드를 먼저** 만들었다.

지금 MiniBlender는 화면에 항상 이 숫자들이 떠 있다.

- 드로우콜 수
- 삼각형 수
- **CPU 시간** (명령을 쌓는 데 걸린 시간)
- **GPU 시간** (실제로 그리는 데 걸린 시간)
- 프레임 시간 / FPS

---

## 드로우콜이 뭔데

`glDrawElements()` 한 번 = 드로우콜 하나. "이 정점들을, 이 셰이더로, 지금 그려라"라고 GPU에게 명령서를 넣는 행위다.

핵심은 **이 명령이 공짜가 아니라는 것**이다. 호출 한 번마다 이런 일이 벌어진다.

1. 드라이버가 현재 GL 상태(바인딩된 VAO, 셰이더, uniform, 블렌딩...)를 검증한다
2. 그 상태를 GPU가 이해하는 명령 버퍼 형태로 번역한다
3. 커맨드 버퍼에 밀어 넣는다

문제는 **이 비용이 그리는 양과 거의 무관하다**는 점이다. 삼각형 2개를 그리든 20,000개를 그리든 위 절차는 똑같이 밟는다. 그래서 "작은 물체를 많이" 그리는 게 "큰 물체를 적게" 그리는 것보다 훨씬 비싸다.

말로는 이렇게 설명하는데, **실제로 얼마나 비싼지** 궁금해서 직접 쟀다.

---

## 측정 1 — 드로우콜을 늘리면 어떻게 되나

큐브를 격자로 배치하면서 개수를 늘려봤다.

**환경**: RTX 3060 / Release x64 / vsync off / 1280×720
**방법**: 워밍업 120프레임 후 300프레임 평균. UI 렌더링은 제외

| 큐브 | 드로우콜 | 삼각형 | CPU | GPU | 프레임 | 콜당 CPU |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 2 | 13 | 0.014 ms | 0.029 ms | 0.101 ms | — |
| 100 | 102 | 1,213 | 0.050 ms | 0.042 ms | 0.150 ms | 0.49 µs |
| 500 | 502 | 6,013 | 0.185 ms | 0.068 ms | 0.284 ms | 0.37 µs |
| 1,000 | 1,002 | 12,013 | 0.341 ms | 0.093 ms | 0.438 ms | 0.34 µs |
| 2,000 | 2,002 | 24,013 | 0.660 ms | 0.146 ms | 0.767 ms | 0.33 µs |
| 5,000 | 5,002 | 60,013 | 1.582 ms | 0.308 ms | 1.737 ms | 0.32 µs |
| 10,000 | 10,002 | 120,013 | **3.093 ms** | 0.309 ms | 3.234 ms | **0.31 µs** |

보이는 게 두 가지다.

**첫째, CPU 시간이 드로우콜 수에 정확히 비례한다.** 콜당 비용이 0.31 µs로 수렴한다. 곱하기만 하면 나온다는 뜻이다.

**둘째, GPU가 놀고 있다.** 10,000개를 그려도 GPU는 0.3 ms인데 CPU는 3.1 ms다. **10배 차이**. GPU는 명령이 오길 기다리는 중이고, 병목은 명령을 만들어 넣는 CPU 쪽이다.

60 FPS = 프레임당 16.6 ms다. 드로우콜만으로 이 예산을 다 쓴다면 약 53,000개. 실제로는 게임 로직·물리·애니메이션이 CPU를 나눠 쓰니 **현실적인 한계는 만 단위 초반**이다.

---

## 측정 2 — 그럼 삼각형이 많으면?

여기서 진짜 궁금한 게 생겼다. 위 표만 보면 "삼각형 12만 개라서 느린 거 아냐?"라고 생각할 수 있다.

그래서 **삼각형 수는 똑같이 두고 드로우콜만 줄인** 케이스를 만들었다. 고해상도 구(16,128 삼각형짜리) 8개를 그린다.

| | 드로우콜 | 삼각형 | CPU | GPU | 프레임 |
|---|---:|---:|---:|---:|---:|
| 큐브 10,000개 | 10,002 | 120,013 | 3.089 ms | 1.643 ms | 3.239 ms |
| **고해상도 구 8개** | **10** | **129,037** | **0.019 ms** | **0.051 ms** | **0.115 ms** |

**삼각형은 오히려 7% 더 많은데**, 드로우콜이 1/1000이 되니까

- CPU **165배** 빨라짐
- 프레임 **28배** 빨라짐

한 발 더 나가서, 구 64개(**삼각형 103만 개** — 큐브 케이스의 8.6배)를 그려봤다.

| | 드로우콜 | 삼각형 | CPU | 프레임 |
|---|---:|---:|---:|---:|
| 큐브 10,000개 | 10,002 | 120,013 | 3.089 ms | 3.239 ms |
| 구 64개 | 66 | **1,032,205** | 0.042 ms | 0.271 ms |

**삼각형을 8.6배 더 그리는데 프레임은 12배 빠르다.**

결론은 명확하다. 요즘 GPU에게 삼각형 100만 개는 아무것도 아니다. **문제는 삼각형이 아니라 "몇 번 부탁했느냐"다.**

## 어떻게 쟀나 — GPU 시간 측정의 함정

여기서 한 번 걸렸던 부분을 적어둔다.

처음엔 CPU에서 시계를 재려고 했다. `glDrawElements` 전후로 시간을 찍으면 되는 줄 알았는데, **그건 GPU 시간이 아니다.** GL 명령은 비동기라서, CPU는 명령서를 큐에 넣고 바로 돌아온다. GPU가 실제로 그리는 건 한참 뒤다. 그래서 CPU에서 잰 값은 "명령서 쓰는 데 걸린 시간"일 뿐이다.

진짜 GPU 시간은 `GL_TIME_ELAPSED` 쿼리로 잰다. GPU 타임라인 위에 직접 스톱워치를 꽂는 방식이다.

```cpp
glBeginQuery(GL_TIME_ELAPSED, query);
//... 렌더링 ...
glEndQuery(GL_TIME_ELAPSED);

GLuint64 ns;
glGetQueryObjectui64v(query, GL_QUERY_RESULT, &ns);  // ← 여기가 함정
```

마지막 줄이 문제다. 결과를 **그 프레임에 바로** 물어보면, GPU가 끝날 때까지 CPU가 멈춰 선다(파이프라인 스톨). **계측기가 계측 대상을 왜곡하는** 상황이다.

그래서 쿼리를 3개 만들어 돌려쓰면서, **3프레임 전 결과**를 읽는다. 그때쯤이면 GPU가 이미 끝냈으니 기다릴 일이 없다.

```cpp
int oldest = (frameIndex + 1) % QUERY_COUNT;
GLint available = 0;
glGetQueryObjectiv(queries[oldest], GL_QUERY_RESULT_AVAILABLE, &available);
if (available)  // 안 끝났으면 이번 프레임은 그냥 건너뛴다
{
    GLuint64 elapsedNs = 0;
    glGetQueryObjectui64v(queries[oldest], GL_QUERY_RESULT, &elapsedNs);
    gpuMs = (float)(elapsedNs / 1000000.0);
}
```

**CPU와 GPU를 따로 보는 것**도 중요하다. 둘을 합쳐 놓으면 병목을 못 찾는다.

- CPU만 높다 → 드로우콜·상태 변경이 병목 → **배칭 / 인스턴싱**
- GPU만 높다 → 픽셀·정점 부하가 병목 → **컬링 / LOD / 셰이더 최적화**

이번 측정에서 CPU 3.09 ms vs GPU 0.31 ms가 나왔으니, 이 씬은 **명백한 CPU 바운드**다. 그럼 답은 정해졌다. 콜 수를 줄여야 한다.

## 코드에서 드로우콜은 어디서 나가나

이제 실제 코드를 보자. MiniBlender에서 드로우콜이 나가는 곳은 **딱 두 군데**다. 둘 다 `Renderer.cpp` 안에 있다.

### 호출 경로

```
main.cpp:124   stats.BeginFrame()          카운터 0으로 리셋 + GPU 타이머 시작
main.cpp:161   renderer.RenderScene(...)   여기서부터 렌더러 안으로
                 │
                 ├─ Renderer.cpp:65   glDrawElements()   ← 오브젝트마다 1개
                 └─ Renderer.cpp:89   glDrawArrays()     ← 그리드용 1개
                 
main.cpp:168   stats.EndFrame()            GPU 타이머 종료 + 숫자 확정
```

드로우콜을 내는 코드가 렌더 루프에 흩어져 있지 않고 `Renderer` 안에만 있는 게 중요하다. 이 위치를 하나로 모아놨기 때문에 **나중에 인스턴싱으로 바꿀 때 여기만 고치면 된다.**

### 1패스 — 오브젝트 (`Renderer.cpp:48`)

```cpp
//--- 1패스: 불투명 오브젝트 ---
//지금은 오브젝트 하나에 드로우콜 하나 = 가장 순진한 방식.
objectShader->use();
objectShader->setMat4("view", view);              // ← 루프 밖: 프레임당 1번
objectShader->setMat4("projection", proj);
objectShader->setVec3("lightDir", glm::normalize(lightDirection));

for (const SceneObject& obj : scene.GetObjects())
{
    if (!obj.visible || obj.mesh == nullptr)
        continue;

    objectShader->setMat4("model", obj.transform.GetMatrix());   // ← 루프 안: 오브젝트당
    objectShader->setVec3("objectColor", obj.color);             //    uniform 2번 +

    glBindVertexArray(obj.mesh->GetVAO());                       //    VAO 바인딩 1번 +
    glDrawElements(GL_TRIANGLES, obj.mesh->GetIndexCount(),      //    드로우콜 1번
                   GL_UNSIGNED_INT, nullptr);

    stats.AddDrawCall(obj.mesh->GetTriangleCount());
}
```

**루프 안과 밖을 나눠 놓은 게 이미 최적화의 시작이다.** `view`/`projection`은 모든 오브젝트가 공유하니 루프 밖에서 한 번만 올린다. 이걸 루프 안에 넣으면 드로우콜 10,000개에 uniform 업로드가 40,000번이 된다.

그래도 남은 건 오브젝트마다 **uniform 2번 + VAO 바인딩 1번 + 드로우콜 1번**. 앞서 잰 콜당 0.31 µs는 사실 이 네 개를 합친 비용이다.

### 2패스 — 그리드 (`Renderer.cpp:70`)

```cpp
gridShader->use();
gridShader->setMat4("invViewProj", glm::inverse(viewProj));
gridShader->setMat4("viewProj", viewProj);
gridShader->setVec3("camPos", camera.GetPosition());
gridShader->setFloat("farPlane", camera.GetFar());

glBindVertexArray(emptyVAO);
glDrawArrays(GL_TRIANGLES, 0, 3);   //버텍스 3개로 화면 전체 = 드로우콜 1개
stats.AddDrawCall(1);
```

무한히 뻗는 바닥 격자 전체가 **드로우콜 1개, 정점 3개**다. 격자를 선 지오메트리로 만들었다면 라인 수만큼 정점과 콜이 늘었을 텐데, 화면을 덮는 삼각형 하나를 두고 프래그먼트 셰이더에서 격자를 계산하기 때문에 이게 가능하다.

`emptyVAO`는 정점 데이터가 하나도 없는 빈 VAO다. Core 프로파일이 "VAO는 뭐라도 바인딩돼 있어야 한다"고 요구해서 형식상 만들어 둔 것이고, 정점 좌표는 셰이더가 `gl_VertexID`로 만들어낸다.

### 카운터는 어디서 올라가나 (`FrameStats.h:27`)

```cpp
void AddDrawCall(unsigned int triangleCount)
{
    drawCalls++;
    triangles += triangleCount;
}
```

`glDrawElements` 바로 다음 줄에서 이걸 부른다. 그래서 화면의 숫자는 추정치가 아니라 **실제로 나간 콜의 개수**다.

삼각형 수는 `GetIndexCount() / 3`으로 계산한다(`Mesh.h:36`). 인덱스 3개가 삼각형 하나니까.

### 기준선을 정직하게

이 코드는 **가장 순진한 방식**이다. 일부러 이렇게 뒀다. 이게 기준선이고, 앞으로 이 숫자를 어떻게 깎는지가 이 프로젝트의 본론이니까.

대신 구조는 미리 갈라놨다. `Mesh`는 데이터(VAO/VBO/EBO)만 들고 있을 뿐 **그리는 법을 모른다.** 그리는 건 `Renderer`만 한다. 인스턴싱이나 MultiDrawIndirect로 갈아끼울 때 **제출하는 쪽(`Scene`, `SceneObject`)은 안 건드리고 실행하는 쪽만** 바꾸려는 것이다.

## 다음에 할 것

콜 수를 줄이는 방법은 단계가 있다. 위에서부터 쉽고, 아래로 갈수록 효과가 크다.

1. **상태 정렬** — 같은 셰이더·재질끼리 모아서 그린다. 상태 변경 자체가 비용이라
2. **UBO** — 카메라 행렬처럼 모든 오브젝트가 공유하는 값을 한 번만 올린다
3. **인스턴싱** — 같은 메시 N개를 `glDrawElementsInstanced` **한 번**으로. 큐브 10,000개가 드로우콜 1개가 된다
4. **프러스텀 컬링** — 화면 밖 오브젝트는 명령 자체를 안 만든다
5. **MultiDrawIndirect + 버텍스 풀링** — 서로 **다른** 메시들까지 한 번의 콜로. 여기가 종착지
6. **GPU 컬링** — 컬링 판정마저 compute 셰이더로 넘겨서 CPU를 완전히 비운다

3번만 해도 위 표의 3.09 ms가 어디까지 떨어지는지 볼 수 있을 것 같다. 다음 글에서 인스턴싱을 넣고 **같은 조건으로 다시 재서** 비교하겠다.

숫자로 확인하지 않으면 안 넣은 거나 마찬가지니까.
